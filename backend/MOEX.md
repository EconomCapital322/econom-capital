# Получение рыночных ставок MOEX

Коннектор `web.integrations.moex:fetch_rates` читает готовую таблицу `yearyields` из [MOEX ISS](https://iss.moex.com/iss/engines/stock/zcyc/securities.json?date=2026-07-31&iss.only=yearyields&iss.meta=off). Это опубликованные точки КБД, а не доходности отдельных ОФЗ и не самостоятельно восстановленная кривая из коэффициентов. Ставки остаются в процентах годовых; сроки уже выражены в годах. Время источника — московское.

Пример настроек локального загрузчика (таймауты — параметры локального стенда):

```dotenv
INTEGRATIONS__FETCH_FUNCTION=web.integrations.moex:fetch_rates
LOADER__MAX_ATTEMPTS=3
LOADER__BACKOFF_BASE_SECONDS=1
LOADER__BACKOFF_CAP_SECONDS=5
LOADER__REQUEST_TIMEOUT_SECONDS=20
```

После настройки DATABASE__DSN, из backend:

```sh
uv run python -m web.processes.moex_loader --report-date 2026-10-30
```

Эта standalone-команда обрабатывает одну дату без постановки расчёта. Для расписания и автоматического расчёта используйте гибридный worker, описанный ниже. Пустой корректный ответ означает отсутствие данных. Другая дата, смешанные снимки времени, дубликаты сроков и некорректные числа отвергаются целиком. Сетевые ошибки, 408/425/429/5xx передаются существующему Loader для ограниченных повторов. Числа из JSON читаются как Decimal.

Не загружайте реальные ставки поверх синтетической истории той же даты: используйте отдельную БД. Сохранённые результаты воспроизводятся по собственным снимкам. `demo_history` и `demo-calculation-spec.json` остаются синтетическими.

Для расчёта на рыночных данных требуется отдельная согласованная спецификация с `data_provenance=market`, сеткой сроков и версией стрессового сервиса. Демонстрационная сетка `demo-*` автоматически не меняется. Коннектор не вводит новую методику, сетку или day count.

## Локальная проверенная связка

`compose.market.yaml` поднимает отдельную постоянную БД `irrbb_moex`. Синтетическая БД из `compose.demo.yaml` не изменяется. Порт Docker динамический: после создания/пересоздания контейнера его нужно получить командой `docker compose -f compose.market.yaml port postgres-market 5432` и указать в DATABASE__DSN. Если Docker не запущен, сначала `docker desktop start`; не продолжать настройку с пустым портом.

На текущем локальном стенде подготовлены игнорируемые Git файлы `.env.moex.local` и `.env.moex-spec.local.json`. Они не входят в репозиторий и не являются производственными настройками. Целевая сетка взята из Excel «практика_Т1_спринт1.xlsx», Лист1!B2:X3: 23 бакета от 1d до 50y. Метки бакетов не равны расчётным тенорам: например, 6m → 0.375 года, 50y → 47.5 года. Версионируемый профиль: examples/moex-excel-grid-spec.json. Коннектор пока получает 11 опубликованных опорных точек MOEX; они являются входом, а не целевой сеткой. Интерполяция и экстраполяция остаются в существующем Go-модуле; иной расчётный горизонт требует согласованной сетки. Day count в этом профиле явно обозначает отсутствие пересчёта дат, поскольку источник передаёт сроки в годах.

Версия стрессового HTTP-сервиса сохранена из ранее проверенной локальной конфигурации (`demo-only-go-stress`): это существующая метка развёрнутой реализации, а не происхождение входных ставок. Значение data_provenance нового профиля — market. Перед производственным запуском владелец Go-сервиса должен согласовать метку версии; API Go сам её не подтверждает.

Остановить старые API/worker через Ctrl+C. В каждом новом терминале, из backend:

```sh
source .env.moex.local
uv run uvicorn web.app:create_app --factory --host 127.0.0.1 --port 8000
```

В отдельном терминале, также из backend:

```sh
source .env.moex.local
uv run python -m web.processes.calculation_worker
```

Go stress-service должен работать на 127.0.0.1:8081. Каталог с собранным base-curve должен быть в PATH worker (локальный профиль добавляет base/bin). Фронтенд запускается обычным `npm run dev` и остаётся в режиме api.

Загрузить ещё одну дату можно из backend:

```sh
source .env.moex.local
uv run python -m web.processes.moex_loader --report-date 2026-10-30
```

Standalone Loader сохраняет только ставки. В обычном интерфейсе выбор даты вызывает идемпотентную подготовку через /api/v1/curve-preparations, после чего объединённый worker загружает отсутствующие ставки и ставит стандартный расчёт. Гибридное расписание описано ниже.

## Гибридная автоматизация

Начиная с миграции 0007 доступна долговечная очередь curve_preparation. Требуется миграция и перезапуск API/worker; старый worker расчётов не умеет обрабатывать новую очередь. Существующие ставки и результаты миграция не меняет.

```dotenv
AUTOMATION__ENABLED=true
AUTOMATION__RUN_AT=19:15:00
AUTOMATION__LOOKBACK_DAYS=7
```

19:15 — параметр локального стенда, не утверждение о гарантированном времени публикации MOEX. Часовой пояс — Europe/Moscow. Worker проверяет расписание раз в минуту, а после перезапуска подхватывает пропуски за lookback_days. Даты без публикации получают no_data. Для недавних no_data/failed повтор возможен раз в следующий день в пределах окна, чтобы обнаружить запоздалую публикацию. Праздничные даты не выдумываются: отсутствие проверяется по самому MOEX. Готовая историческая дата автоматически ежедневно не перезагружается.

POST /api/v1/curve-preparations принимает {"reportDate":"2026-10-28","retry":false}. Возвращает 202 для queued/running и 200 для ready/no_data/failed. Повторы и несколько вкладок объединяются по дате; HTTP не ждёт MOEX. GET /api/v1/curve-preparations?reportDate=2026-10-28 только читает состояние. Ответ: reportDate, status (idle/queued/running/ready/no_data/failed), runId и errorCode. runId/errorCode могут быть null. ready означает, что ставки готовы и стандартный расчёт поставлен/найден; готовность результата определяется отдельно обычным API расчётов.

Worker теперь совмещает обработку загрузки и прежние базовый/стрессовый этапы. Получение ставок не удерживает транзакцию или соединение БД. Сохранение ставок, создание стандартного запуска и завершение подготовки атомарны. Heartbeat продлевает lease, истёкшее задание подхватывается повторно, старый владелец не может опубликовать результат. Штатная остановка возвращает незавершённую загрузку в очередь. Расчёт продолжится после закрытия вкладки. Параметры пользовательского перерасчёта и сохранённые снимки остаются независимыми.

Загрузить интервал истории один раз:

```sh
source .env.moex.local
uv run alembic upgrade head
uv run python -m web.processes.backfill --from 2026-09-01 --to 2026-10-31
uv run python -m web.processes.calculation_worker
```

Backfill пропускает даты с существующей подготовкой или стандартным рыночным запуском. Готовые запуски видны в отчёте со своим `runId`. Даты без публикации имеют статус `no_data`, ошибки — `failed` с кодом причины. Неполный или несогласованный набор MOEX даёт `INVALID_MARKET_DATA`, сбой источника — `SOURCE_UNAVAILABLE`, прочая ошибка подготовки — `PREPARATION_FAILED`. Ошибки уже сохранённых расчётов отображаются с их кодом расчёта. Backfill не сбрасывает ошибки и отметки об отсутствии публикации.

Для шестимесячной истории используйте границы полных календарных месяцев. Например, на 20 ноября 2026 года это 1 мая — 31 октября:

```sh
uv run python -m web.processes.backfill --from 2026-05-01 --to 2026-10-31 --output history.json
# После обработки очереди обновить отчёт без записи в БД:
uv run python -m web.processes.backfill --from 2026-05-01 --to 2026-10-31 --report-only --output history.json
```

В отчёте `ready` означает завершённый расчёт. `queued` и `running` обозначают подготовку или ещё не завершённый расчёт. `missing` означает, что дата пока не обработана и не стоит в очереди. В локальной рыночной БД обработаны сентябрь и октябрь: 44 даты с настоящими ставками, 17 дат без публикации. Дополнительно в браузере проверена отсутствующая дата 14 августа: выбор автоматически загрузил MOEX и получил 7 кривых.

Прежняя standalone-команда moex_loader остаётся инструментом загрузки одной даты без расчёта, для совместимости. В рабочем гибридном сценарии используются очередь подготовки и объединённый calculation_worker; не требуется отдельный постоянно работающий loader. Для ежедневной работы worker и компьютер должны быть включены.

## Исправление сетки по Excel

Локальный профиль `.env.moex.local` теперь указывает на `examples/moex-excel-grid-spec.json`; прежняя локальная копия `.env.moex-spec.local.json` также исправлена. Они содержат сетку Лист1!B2:X3, 23 бакета. Сроки берутся из строки 3 без пересчёта из подписей строки 2. Колонки Y:AC не включены: в них нет полного набора подписей и расчётных теноров, а Y16 ссылается на пустую Y3. Контроль Go `TestBuildExcel` сверяет все 23 базовые ставки B17:X17 на 19 исходных точках B4:T4/B15:T15, включая экстраполяцию по двум последним опорным точкам.

Важно: живой ISS yearyields возвращает 11 опорных сроков, тогда как Excel содержит 19 округлённых исходных ставок. На живых данных применяется та же линейная методика и та же целевая сетка, но числовое совпадение с округлённым историческим Excel не обещается. Отсутствующие в ISS опорные значения не подменяются ставками Excel. Контроль Excel выполняется отдельно на его собственном полном входе.

После смены спецификации нужен новый полный запуск, а не стрессовый перерасчёт на старой базе. Сохранённые результаты с 11 сроками остаются в истории. Перезапустите worker с `.env.moex.local`: фоновая подготовка загружает спецификацию при старте процесса. API читает файл спецификации при создании полного запуска. Открытая ссылка на старый runId продолжает показывать старый результат; для актуального выберите дату без runId или новый запуск в истории.

Проверено после исправления: 53 новых стандартных расчёта на реальных сохранённых ставках завершились ready с 23 точками в каждой кривой. В браузере за 31.07 отображаются 23 строки и полный CSV из 161 строки. Старые 11-точечные запуски не удалены и не перезаписаны.
