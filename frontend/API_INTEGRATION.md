# Интеграция фронтенда с FastAPI

## Источник контракта

Использована текущая реализация `backend/src/web/routes/curve_runs.py`, схемы `requests.py` / `responses.py`, сервис `RunService` и модели репозиториев. Ссылки backend README на `docs/api.md` ведут в отсутствующий в этом checkout каталог `docs`; недостающий документ не подменялся старой внешней версией.

## Подключённые операции

| Операция | Назначение |
| --- | --- |
| GET `/api/v1/input-rates?reportDate=YYYY-MM-DD` | Наличие и исходные ставки выбранной даты |
| GET `/api/v1/curve-runs?reportDate=YYYY-MM-DD` | Восстановление последнего сохранённого запуска |
| GET `/api/v1/curve-runs/{runId}` | Состояние: queued / running / ready / failed, этап base / stress |
| GET `/api/v1/curve-runs/{runId}/result` | Семь готовых кривых и использованные параметры |
| POST `/api/v1/curve-runs` | Явный пользовательский запуск, если ещё нет сохранённой базы |
| POST `/api/v1/curve-runs/{runId}/recalculations` | Явный перерасчёт на сохранённой базе родителя |

Просмотр даты, вкладок и линий не создаёт запуск. Если на сервере уже есть queued/running, фронт опрашивает состояние каждые 1,5 секунды. После ready/failed или ошибки запроса опрос прекращается. Смена даты отменяет только чтение, не серверное задание. После повторного открытия список запусков восстанавливает последний результат или активное задание. Внешний вид выбора истории не добавлялся: интерфейс открывает последний запуск за дату.

POST не повторяется автоматически. После потери ответа обновляется список запусков, поскольку сервер мог уже принять задание. До завершения отправки повторный клик блокируется синхронным ref. Перерасчёт использует runId родителя и его снимок, а не текущие обновлённые исходные ставки.

## Код

- `src/api/httpContract.ts` — DTO, проверка ответов во время выполнения, перевод snake_case **кодов сценариев** в внутренние коды. Поля HTTP JSON — camelCase, как в реальном FastAPI.
- `src/api/httpAdapter.ts` — HTTP-запросы, ограничение ожидания, безопасные сообщения, сохранённые запуски и POST.
- `src/hooks/useRemoteCurves.ts` — TanStack Query / Mutation, опрос состояния, защита по дате и запуску.
- `src/api/index.ts` — выбор API по умолчанию; только `VITE_API_MODE=demo` включает локальную Excel-фикстуру.
- `src/App.tsx` — подключение серверных состояний к существующему интерфейсу; локальный расчёт в API-режиме выключен.

Ставки API `ratePercent` уже в процентах годовых, параметры — в п.п. Деления/умножения на 100 нет. Сырые исходные ставки не рисуются как построенная базовая кривая. Полный результат проверяется по дате, runId, всем семи кодам, сетке и использованным параметрам. Приведённая в state базовая кривая сверяется с result. JSON numbers читаются как JS number; серверный Decimal сверх точности double не сохраняется побитово. Это ограничение браузерной модели чисел, ставки для отображения округляются существующим форматтером.

Показывается фактическая дата/время публикации источника в МСК. Расчётные ошибки переведены в короткие сообщения без traceback, SQL и серверных технических сообщений.

## Выгрузка

В текущем FastAPI нет ручек CSV/XLSX/SVG. Сохранён CSV, сформированный из **реального полного ответа**: все семь кривых, дата, бакет, тенор, ставки и параметры готового результата. Выбор отображаемых линий состав CSV не меняет. BOM и экранирование сохранены. Новые ручки и прямой доступ к Go/MOEX не добавлены.

## Открытые расхождения с требованиями

1. **Максимум P/K/D:** требуемый диапазон — `(0,50]` п.п. FastAPI, хранение, БД и Go проверяют этот диапазон. Во фронтенде остаётся обновить проверку ответа в `httpContract.ts` и текст ошибки в `httpAdapter.ts`. Значения не обрезаются и не подменяются.
2. **Автоматический запуск:** MOEX Loader только сохраняет исходные ставки и не создаёт curve_run. Выбор даты во фронте поэтому не может честно гарантировать автоматический расчёт. При наличии ставок без запусков показано отсутствие готового расчёта и доступна кнопка явного запуска. Добавлять скрытый POST на просмотр даты не стали. Backend должен запускать стандартный расчёт после загрузки/публикации ставок.
3. **Производственная математика и MOEX:** Python Worker не имеет подключённых реальных fetch/base/stress функций; Go-сервис в `stress` существует, но не подключён к Python SlavaAdapter. Нет согласованного `CALCULATION__SPEC_FILE` с реальной сеткой/версиями/method/day_count. Эти значения не придуманы во фронтенде. Без настроек POST даст 503 либо Worker переведёт принятый запуск в failed.
4. **Регламент обновления:** внешний планировщик и производственные функции/календарь должны быть настроены на стороне backend.

Это рабочая HTTP-связка с текущим API, но не завершённая производственная цепочка MOEX → реальные алгоритмы → результат.

## Проверка вручную

Чек-лист основного сценария находится в [README.md](README.md#проверка). Перед проверкой подними FastAPI, PostgreSQL и Worker с корректными настройками.

Команды статической проверки и сборки: `npm run typecheck`, `npm run lint`, `npm run build`. Автотесты, браузерные тестовые страницы и HTTP-проба удалены из фронтенда по решению команды; зависимости для их запуска не требуются.

При первоначальном подключении обмен Vite → FastAPI → PostgreSQL → Worker был проверен на изолированной базе. Успешные вычисления использовали явные маркерные функции backend, а не производственную математику. Описанные выше ограничения реальной цепочки остаются актуальными. Визуальная проверка в браузере в сессии интеграции не выполнялась: browser use был выключен в настройках Work.
