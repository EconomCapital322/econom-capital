# Подготовка фронтенда к API

## Что найдено в репозитории

На момент проверки в рабочем дереве нет описания HTTP API, OpenAPI/Swagger, серверных маршрутов или DTO. Фронтенд уже содержит основной экран, демонстрационный адаптер, локальный расчёт и экспорт CSV; запуск и ограничения описаны в frontend/README.md. Ранее обсуждавшиеся внешние документы не считаются актуальным контрактом репозитория.

Поэтому HTTP-клиент с адресами ручек, авторизацией, серверными статусами и DTO пока не реализован. Сетевых запросов к MOEX нет.

## Что подготовлено

- `src/api/types.ts`: внутренний интерфейс `CurvesAdapter`, входные и выходные модели получения базовой кривой и полного расчёта. Это модели приложения, **не предполагаемый формат HTTP JSON**.
- `src/api/demoAdapter.ts`: демонстрационная реализация. Только она читает Excel-фикстуру и управляет искусственной ошибкой/отсутствием данных.
- `src/api/index.ts`: точка выбора реализации и `apiBaseUrl` из `VITE_API_BASE_URL`. Переменная зарезервирована для будущего HTTP-адаптера; её заполнение само по себе не переключает демонстрационный режим.
- `src/store/CurvesApiContext.ts`: внедрение адаптера. В `main.tsx` подключены контекст и `QueryClientProvider`.
- `src/hooks/useCurvePreview.ts`: TanStack Query, отдельный ключ для каждой даты и демонстрационного режима, отмена через AbortSignal, отсутствие подстановки данных другой даты, ручная повторная попытка при ошибке.
- `src/hooks/useCurveCalculation.ts`: запуск через интерфейс адаптера, защита от двойного запуска, отмена при смене даты и защита от позднего результата. Состояния idle/running/ready/error — состояния интерфейса, не статусы сервера. Автоматический retry расчёта не включён, чтобы не создавать дубликаты.
- `src/hooks/useDemonstration.ts`: управление явно обозначенными демонстрационными состояниями. Если внедрить сервис без `demonstration`, инструмент демонстрации и подписи прототипа скрываются.
- `.env.example`: только пустой `VITE_API_BASE_URL`. Значения VITE_* попадают в браузерную сборку, секретов в них быть не должно.

## Что нужно получить от бэкенда

1. Базовый URL, версия API, точные методы и пути ручек.
2. Формат запроса получения данных за дату; ответ при наличии/отсутствии исходных ставок. Названия полей, формат дат/времени и часовой пояс.
3. Формат запуска расчёта: какие поля передавать, единицы P/K/D, связь с базовой кривой/источником.
4. Синхронный ли расчёт. Если асинхронный — идентификатор, точные статусы, ручка проверки результата и правила polling. Не предполагаем ни polling, ни WebSocket до подтверждения.
5. Формат полного результата: сценарии и их коды, бакеты, теноры, единицы ставок и параметров, точность, дата источника и метаданные расчёта.
6. Формат ошибок и HTTP-коды, отдельно отсутствие данных, неверные параметры и ошибка расчёта.
7. Авторизация: нужна ли, каким способом; настройки CORS/cookies, если применимы.
8. Сохраняются ли несколько расчётов за дату. Если да — ручки списка и одного результата, сортировка/пагинация, время создания и параметры для понятного выбора. Технический ID остаётся внутренним. Выбор расчёта не добавлен: сначала нужны контракт и согласованный вариант в макете.
9. Семантика повторного запуска/идемпотентность и возможность отмены. AbortSignal сейчас отменяет ожидание на фронтенде; это не утверждение об отмене серверного задания.
10. Серверная выгрузка, если она требуется. Текущий CSV остаётся локальным экспортом успешно полученного полного результата.

## Как подключить реальный сервер

1. Согласовать контракт и добавить его в репозиторий.
2. Реализовать `CurvesAdapter` в `src/api`: использовать `apiBaseUrl`, точные DTO и согласованный способ авторизации. Проверять ответ и преобразовывать его во внутренние модели. Не отправлять базовые точки из браузера, если контракт требует только дату/ID.
3. Если API асинхронный, реализовать подтверждённый протокол ожидания внутри адаптера либо расширить интерфейс/хуки после согласования. Не подменять серверные статусы существующими названиями UI-состояний.
4. В `src/api/index.ts` заменить создание демонстрационного сервиса на `{ adapter: realAdapter }`. Компоненты и хуки продолжают работать через общий интерфейс.
5. Заполнить локальный `.env.local` по `.env.example` и перезапустить Vite. Проверить реальные сценарии, ошибки, отмену и единицы измерения.

Список сохранённых расчётов намеренно не смоделирован: наличие такой функции в актуальном API пока неизвестно.

## Актуальные ограничения расчёта

- Выбор даты в демонстрации автоматически рассчитывает кривые со стандартными параметрами. Это локальный прототип, а не серверное сохранение.
- Идентичные базовые ставки не запускают новый расчёт; изменение числовых входных данных отменяет ожидание прежнего и скрывает устаревший результат.
- Кнопка проверки наличия данных вызывает только получение данных за дату, не прямую загрузку MOEX.
- Проверка базовой кривой результата сейчас точная, по нормализованным внутренним числам, бакетам и тенорам. Это подходит для демонстрационной фикстуры. Правила точности/округления реального API ещё должны быть согласованы; произвольный epsilon не задан.
- В реальном адаптере необходимо различать получение/ожидание уже рассчитанного результата и создание ручного перерасчёта по фактическому контракту. Текущий интерфейс адаптера не утверждает наличие двух одинаковых POST-запусков.
- AbortSignal прекращает ожидание фронтенда и не подтверждает отмену задания на сервере.
