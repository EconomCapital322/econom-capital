# Контракт кривых и калькулятора

## Публичный источник

`GET /api/v1/curve-runs/standard-result?reportDate=YYYY-MM-DD` возвращает последний
готовый стандартный результат. Клиент проверяет дату, UUID runId, рыночное происхождение,
стандартные P/K/D = 4/5/3, семь разных сценариев, конечные JSON numbers,
положительные DF и единую возрастающую сетку с уникальными подписями бакетов.
Неполный комплект не используется. Внутренние snake_case/десятичные строки Go не принимаются.

Коды сценариев в калькуляторе совпадают с API: `base`, `parallel_up`, `parallel_down`,
`steepener`, `flattener`, `short_rate_up`, `short_rate_down`. `all` — только переключатель
клиента для семи независимых оценок, а не новый серверный сценарий.

## calendar-bucket-v1

Рабочее правило выбрано по прямому указанию пользователя. Не обозначается как
подтверждённая экспертом банковская методика.

Используются календарные верхние границы от отчётной даты:
1 день; 1, 3, 6, 9, 12, 18 месяцев; 2, 3, 4, 5, 6, 7, 8, 9, 10, 15, 20,
30, 35, 40, 45, 50 лет. Им соответствуют 23 подписи сетки Excel из API.
Если числа в целевом месяце нет, граница приходится на последний день этого месяца.
Каждый интервал открыт слева и закрыт справа. Например, платёж ровно через три
календарных месяца относится к `3m`, на следующий день — к `6m`.

Для каждого платежа определяется интервал по его фактической дате. Берётся **готовый
discountFactor этой точки выбранной кривой**, а сохранённый `tenorYears` выводится
в отчёт для проверки. Это представитель интервала, а не срок конкретного платежа.
DF не интерполируется и не рассчитывается заново. Исходная 19-бакетная агрегация
калькулятора остаётся самостоятельным отчётом и не используется для выбора DF.
Платежи свыше 20 лет не сворачиваются в один бакет: сохраняется различие до 50 лет.
Платежи на/до отчётной даты и за 50-летней границей отклоняются, а не переносятся
к ближайшей точке. Новая сетка с неизвестными подписями также отклоняется.

`PV = amount × discountFactor × sign`, где ASSET имеет знак +1, LIABILITY — −1.
Все операции дисконтирования выполняются Decimal с точностью 34 значащих цифры.
Нет принудительного округления DF или сумм PV до копеек. У ставки кривой сохраняется
исходная единица `% годовых`. У договорной ставки сделки остаются доли по контракту ядра.

Результат — приведённая стоимость уже рассчитанных договорных потоков.
Это не самостоятельный расчёт Economic Capital и не прогноз новых плавающих купонов
по стрессовой кривой. Если команде 1 потребуется дисконтирование на точную дату
каждого платежа или переоценка самих плавающих потоков, методика и API расширяются явно.

## Восстановление и ошибки

Нет готового результата: один POST `/curve-preparations`, GET подготовки,
GET запуска, GET результата по его runId. Параллельные клиенты объединяются сервером.
HTTP-сбой нашего API не называется ошибкой MOEX без известного серверного кода.
Известные причины подготовки переводятся в безопасные сообщения, внутренний message
не печатается. Клиент не сбрасывает failed/no_data автоматически через retry=true.
Для повторной подготовки после исправления причины используется существующий интерфейс
кривых. Новый запуск клиента повторно читает готовый результат и состояние.

Для запуска на нескольких датах нужны отдельные выходные каталоги. CLI не имеет
общего изменяемого выбранного дня, поэтому поздний ответ не может переключить дату
другой попытки. Файл статуса относится только к данной выходной папке.
